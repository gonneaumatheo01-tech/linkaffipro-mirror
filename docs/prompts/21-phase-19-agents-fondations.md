## Règles non négociables (plan validé, section « Niveaux d'autonomie et garde-fous »)
1. **Logique programmée pour le Grand Chef et les Chefs.** Aucun appel à un modèle d'IA pour décider quoi faire, dans quel ordre, ou quand. L'IA n'est appelée que par les agents Rédaction (écrire) et Contrôle qualité (juger), et plus tard Média IA, Conversations, Synthèse, Ads.
2. **Mode simulation par équipe, actif par défaut.** Tant que `AgentTeamConfig.simulation` est vrai, toute publication est redirigée vers le canal Test (`Channel.isTest`), avec en tête du texte `[SIMULATION équipe Dating → <nom du vrai canal>]`. Rien ne part jamais sur un vrai canal ni vers un vrai membre sans que le client ait désactivé la simulation de l'équipe dans le site (ADMIN). Les tests automatiques tournent toujours en simulation.
3. **Bouton Pause** par équipe (`paused`) et pause générale (`Setting` `agents.pausedAll`) : une équipe en pause ne crée ni ne poursuit aucune mission ; les missions en cours attendent.
4. **Plafonds mensuels** par équipe et par fournisseur (`AgentUsage`) ; une mission qui dépasserait le plafond est refusée proprement (statut `BLOCKED_BUDGET`, motif clair) ; alerte à 80 % et à 100 % (une fois par mois chacune).
5. **Limites de rythme** : maximum de posts par jour et par canal (`ChannelAgentPlan.postsPerDay`), espacement minimal entre deux posts d'un même canal (`minSpacingMinutes`, 90 par défaut), fenêtre horaire autorisée (`windowStart`/`windowEnd`, Europe/Paris), heures calmes. Les limites Telegram existantes (`telegram-send`) restent telles quelles.
6. **Règles de contenu vérifiées par le code** (`packages/agents/src/rules/content.ts`, pures, testées) : jamais de mention d'IA ni d'assistant dans un post (liste de tournures en 6 langues, comme `packages/chat` le fait pour le déni) ; aucun lien en dehors des liens suivis de la plateforme (`go.goolink.eu`, `TrackingLink`) ; longueur maximale réglable (900 caractères par défaut, le client veut des légendes très courtes) ; mots interdits réglables par équipe ; HTML Telegram valide (`packages/core/src/telegram-html.ts`).
7. **Mise en pause automatique** d'une équipe après 3 missions échouées de suite, avec alerte Telegram.
8. **Journal complet** : chaque action d'agent = un `Event` (famille « Agents », sans texte complet des posts : identifiants et résumés), chaque action humaine (validation, refus, changement de réglage) = un `AuditLog`.
9. **Aucun secret dans le code, git ou les messages.** Les clés des fournisseurs (phases suivantes) se saisissent dans le site et vivent chiffrées dans `Setting` (`packages/core/src/crypto.ts`, comme `assistant.venice`), jamais renvoyées au navigateur.
10. **Link Affi** reste en lecture seule (rien ne change).

## Architecture (plan, section « Intégration avec LinkAffiPro »)
- Nouveau paquet **`packages/agents`** (`@linkaffipro/agents`), consommé en TypeScript source comme les autres, sans import de Next.js ni de grammY :
  - `src/types.ts` : `TeamKey = "dating" | "casino" | "sports" | "algo"`, `AgentKey` (`mediatheque`, `media-ia`, `redaction`, `cotes`, `capture`, `planification`, `controle`, `publication`, `posts`, `horaires`, `conversations`, `experimentation`, `synthese`, `ads` ; seules les clés de cette phase ont un agent réel, les autres sont déclarées), `Mission`, `MissionStep`, `AgentContext` (prisma, logger, horloge injectable `now()`, fournisseurs, réglages, `enqueue`), `AgentResult` (`ok`, `output`, `costCents`, `needsValidation?: { reason }`, `retryable?`, `error?`).
  - `src/agents/<cle>/index.ts` : `export const agent: AgentDefinition = { key, run(mission, ctx) }`. Un agent = une fonction pure vis-à-vis du réseau : tout fournisseur externe passe par `ctx.providers`, avec un faux fournisseur pour les tests et le mode simulation.
  - `src/chiefs/<equipe>.ts` : la chaîne d'étapes de l'équipe (liste ordonnée de clés d'agents + règles de branchement, par exemple « pas de vidéo disponible → post texte ») et `runNextStep(missionId)`.
  - `src/orchestrator/` : `plan-day.ts` (missions à créer aujourd'hui par équipe et par canal), `budgets.ts`, `collisions.ts`, `autonomy.ts` (ce qui doit être validé selon le niveau), `pause.ts`, `reports.ts` (rapport quotidien), `resume.ts` (missions bloquées à reprendre).
  - `src/rules/` : règles pures (`content.ts`, `similarity.ts` pour les doublons, `slots.ts` pour les créneaux).
  - `src/providers/` : interfaces (`llm.ts` au-dessus du client de `packages/ai`, `video.ts`, `image.ts`, `odds.ts`, `screenshot.ts`) et `fake.ts`. Dans cette phase, seul `llm` a une vraie implémentation.
- **Missions reprenables** : `AgentMission.steps` (JSON : `{ agent, status, startedAt, endedAt, summary, costCents, error }[]`) et `currentStep`. Chaque étape est une tâche BullMQ avec `jobId = <missionId>:<index>` (idempotente : une étape déjà terminée est ignorée). Quand une étape se termine, le Chef enfile la suivante. Un balayage `resume` (toutes les 10 minutes, dans `agents-orchestrator`) ré-enfile les missions `RUNNING` sans activité depuis 15 minutes. Une mission ne publie jamais deux fois : `Publication` est idempotente (`AgentMission.postId` posé avant l'envoi).
- **Files BullMQ** (dans `packages/queue/src/jobs.ts`, `apps/worker/src/queues.ts`, un processeur par file dans `apps/worker/src/processors/`, voir son `README.md`) : `agents-orchestrator` (tâche répétée toutes les 30 minutes + à la demande), `agents-dating`, `agents-casino`, `agents-sports`, `agents-algo`, `agents-ads`. Dans une file d'équipe, le **nom de la tâche = la clé de l'agent** (`redaction`, `controle`…) : un agent par action, peu de files. Concurrence 2 par file d'équipe. Les files existantes (`telegram-send`, `scheduler`…) ne changent pas.
- **Publication** : réutilise la création de messages programmés du site. Regarde comment le site crée un `Post` programmé (`apps/web/lib/posts/*`, actions de `apps/web/app/(admin)/messages/`) et extrais la logique de création dans une fonction partagée utilisable par le worker (dans `packages/db` ou un nouveau `packages/posting`, à toi de choisir et de noter), appelée par le site et par l'agent Publication. Le `Post` créé (statut programmé, `scheduledAt`, `mediaAssetIds`, boutons d'offre de la campagne, `publisher` BOT par défaut, ACCOUNT si le texte contient des emojis animés) est envoyé par le scheduler et `telegram-send` existants, sans modification. Le `Post` porte `agentMissionId` (nouvelle colonne nullable) pour relier résultats et mission.
- **Rédaction** : passe par le client Claude existant (`packages/ai/src/client.ts`, clé de Réglages → IA) avec un nouveau prompt système `packages/agents/src/agents/redaction/prompt.ts` : univers, canal, persona ou ton du canal, exemples de style, consignes de style de l'équipe, **liste des 30 derniers posts du canal** (textes courts) pour ne pas se répéter, règles de forme (très court, style Telegram, humain, « rentre dedans », emojis sobres, jamais générique, jamais de mention d'IA). Sortie JSON stricte validée par le code (comme `packages/ai` et `packages/chat` le font) : `{ text, hook, topic }`. Deux modèles réglables dans `AgentTeamConfig` ou `Setting` `agents.models` : un rapide pour les contrôles, un plus fort pour la rédaction (par défaut : ceux de `packages/ai/src/models.ts`).
- **Planification** (`rules/slots.ts`, pur) : choisit `scheduledAt` à partir du plan du canal (`ChannelAgentPlan`), des meilleurs horaires existants (`Setting` `besthours.<channelId>`, `apps/web/lib/besthours`), de l'espacement minimal, des heures calmes, et des posts déjà programmés ou envoyés (collisions), en Europe/Paris, stockage UTC.
- **Contrôle qualité** : (a) règles de contenu (`rules/content.ts`) ; (b) doublon : similarité avec les 30 derniers posts du canal (`rules/similarity.ts`, trigrammes ou Jaccard, seuil réglable) ; (c) média valide (présent, type, durée et taille raisonnables) ; (d) jugement IA facultatif (modèle rapide : « ce texte a-t-il l'air écrit par un humain, respecte-t-il la fiche ? » → oui / non / doute, JSON strict) ; verdict `publier` / `refaire` (une seule fois : renvoie à Rédaction avec le motif) / `valider` (demande humaine). Les règles (a) à (c) sont du code ; (d) ne peut jamais forcer une publication qu'une règle refuse.
- **Médiathèque** (base, enrichie en phases 20 et 22) : réutilise **`MediaAsset`** (octets en base, `MediaAssetTelegramFile` par bot) ; ajoute `AgentMediaTag` (ou des colonnes sur `MediaAsset` : `teamKey`, `theme`, `personaId`, `kind` SOURCE / GENERATED / PHOTO, `origin` HUMAN / AI, `sha256` déjà là) et `MediaUsage` (asset, canal, post, date). Choix du prochain média non utilisé par canal (le moins récemment utilisé, jamais deux fois en 30 jours sur le même canal). **Dépôt par le bot** : un média (vidéo, photo) envoyé ou transféré à l'un de nos bots par l'identifiant Telegram de l'admin (`Setting` `admin.telegramUserId`) avec une légende contenant des mots-clés (`#casino #roulette`, `#dating #source #lea`) est rangé automatiquement (nouveau handler `packages/telegram/src/handlers/media-inbox.ts`, avant le `/start` générique, sur le modèle de `custom-emoji.ts` et `forward.ts`) et le bot confirme en une ligne. Le canal Telegram privé « Médiathèque » du plan est une **copie** facultative (réglage : identifiant du canal ; si renseigné, chaque média rangé y est aussi publié par le bot, ce qui donne un `file_id` réutilisable) ; les octets restent en base comme aujourd'hui. Note la décision.
- **Grand Chef** (`agents-orchestrator`, toutes les 30 minutes) : pour chaque équipe active, non en pause : calcule les missions manquantes du jour (plan par canal moins missions déjà créées), vérifie budgets et collisions, crée les `AgentMission` et enfile la première étape ; applique les niveaux d'autonomie ; relance `resume` ; à 9 h Paris envoie le rapport quotidien (une ligne par équipe : publié, en attente, refusé, dépense du mois) via le dialogue admin (`packages/telegram/src/admin-notify.ts`, `apps/worker/src/reports`).
- **Niveaux d'autonomie** (`AgentTeamConfig.autonomyLevel` 0, 1, 2) et `autonomy.ts` : niveau 0 = toute mission passe en validation avant publication ; niveau 1 = seules les nouveautés (premier post d'un canal, nouvelle persona, nouveau thème, nouvelle catégorie, doute du Contrôle) ; niveau 2 = rien, rapport seulement. Toujours validés quel que soit le niveau : ce que le plan liste par équipe (phases suivantes). Quand une validation est demandée, la mission passe en `WAITING_VALIDATION`, un `AgentValidation` est créé et l'aperçu part par Telegram.

## Validation par Telegram et dialogue admin
- Aperçu envoyé par le bot du dialogue admin (celui de `pnpm tg:send`), au seul identifiant admin (`Setting` `admin.telegramUserId`) : texte du post (ou résumé), média joint s'il y en a un, canal et équipe, motif, et boutons inline **✅ Publier**, **✏️ Corriger** (le prochain message texte de l'admin remplace le texte, puis repasse au Contrôle qualité), **❌ Refuser** (motif facultatif, mission annulée, l'équipe apprend : le motif est journalisé). Callbacks `agv:<id>:ok|edit|no`, acceptés seulement depuis l'identifiant admin (toute autre personne est ignorée, règle de `CLAUDE.md`).
- Le dialogue admin (`packages/telegram/src/admin-chat.ts`) comprend aussi : `agents` (état en 6 lignes), `pause <équipe>` / `reprends <équipe>` / `pause tout` / `reprends tout`, `ok <n>` / `non <n>` pour une validation par son numéro court.
- Une validation sans réponse depuis 24 h : la mission est reportée au lendemain et un rappel part (une seule fois) ; depuis 72 h : annulée, journalisée.

## Demandes au client par Telegram : clés, identifiants, choix, médias (demande du client, 23 octobre 14 h)
- Le client veut que **tout ce qui lui est demandé passe par le bot Telegram** du dialogue admin, pas par le site : clés des fournisseurs, identifiants, adresses, choix, médias. Le site (Réglages → Agents) reste possible en secours, mais la voie principale est Telegram. Ce mécanisme sert à toutes les phases suivantes : construis-le proprement ici.
- Table `HumanRequest` : `teamKey`, `kind` (SECRET, TEXT, CHOICE, MEDIA, CONFIRM), `key` (ce qui est demandé : `providers.fal.apiKey`, `providers.odds.apiKey`, `providers.bookmakers.sportaza.login`, `persona.<id>.loraUrl`…), `question` (texte envoyé), `options` (JSON pour CHOICE), `expected` (JSON pour MEDIA : nombre, mots-clés), `status` (PENDING, ANSWERED, SKIPPED, EXPIRED), `answerSummary` (jamais un secret : pour une clé, seulement « …ab12 »), `askedAt`, `telegramMessageId`, `remindedAt`, `answeredAt`, `missionId?` (la mission qui attend), `onAnswer` (JSON : « vérifier la clé », « reprendre la mission », « lancer le banc d'essai »…).
- **Une seule question à la fois** (règle de `CLAUDE.md`) : les demandes forment une file ; la suivante part quand la précédente est répondue ou passée. Chaque question : 5 lignes au plus, en français simple, ce qu'il faut faire exactement (« Réponds à ce message avec ta clé fal.ai » / « Réponds 1, 2 ou 3 » / « Envoie-moi 5 vidéos avec #dating #source #lea »), le lien à ouvrir s'il y en a un (« Crée ta clé ici : … »), et comment passer (« Réponds "plus tard" »). Un rappel au plus après 24 h ; après 7 jours la demande expire (visible sur le site, relançable en un clic).
- Réponse : de préférence une **réponse Telegram au message de la question** (`reply_to_message`) ; sinon le prochain message privé de l'admin qui n'est pas une commande connue est pris pour la réponse de la demande en cours. CHOICE : numéro ou texte de l'option ; CONFIRM : « oui » / « non » ; MEDIA : les médias arrivent par le dépôt par mots-clés et la demande se clôt quand le nombre demandé est atteint ; TEXT : le texte tel quel (adresse vérifiée si c'est une adresse).
- **Secrets reçus par Telegram** (exception voulue par le client à la règle « jamais de clé dans un message Telegram » de `CLAUDE.md`, qui ne vaut que pour l'envoi : le bot n'envoie jamais une clé) : la valeur est chiffrée et rangée dans `Setting` (`packages/core/src/crypto.ts`) **sans jamais** passer par `Event`, `AuditLog`, un journal, un log ni un message (l'`AuditLog` dit « clé fal.ai enregistrée », l'`Event` n'a pas de texte) ; le bot **supprime aussitôt le message de l'admin** qui contenait la clé (`deleteMessage`, possible en privé pour un message reçu) et confirme avec les 4 derniers caractères seulement ; si une vérification existe (fal, cotes, bookmaker), elle est lancée tout de suite et son résultat renvoyé (« vérification : OK » / « KO : … réessaie ») ; en cas de KO la demande reste ouverte. Le texte brut des messages privés de l'admin n'est jamais journalisé (même traitement que les bots assistants : `Event` sans texte).
- Commandes proactives du dialogue admin : `clé fal <valeur>`, `clé cotes <valeur>`, `bookmaker <nom> <identifiant> <mot de passe>` (message supprimé aussitôt), `budget vidéo <euros>`, `plus tard`, `demandes` (liste des demandes ouvertes), `vrai <équipe>` puis « OUI » (désactive la simulation, CONFIRM obligatoire), `niveau <équipe> <0|1|2>`.
- Les agents créent leurs demandes par `askHuman(…)` (`packages/agents/src/human/requests.ts`) ; une mission qui attend une réponse passe en `WAITING_HUMAN` (nouveau statut) et reprend à la réponse ; les demandes sont aussi visibles et répondables dans `/agents/validations` (onglet « Demandes »), avec les mêmes règles. Toute décision visible par le client en fin de phase (banc d'essai, passage en vrai, niveau) passe par ce mécanisme (CHOICE / CONFIRM, « Réponds OUI pour confirmer »).
- Dans cette phase, une seule demande réelle est créée à la fin : CONFIRM « Veux-tu recevoir chaque matin le rapport des agents ? Réponds oui ou non » (ce qui vérifie le mécanisme en vrai, sans secret).
